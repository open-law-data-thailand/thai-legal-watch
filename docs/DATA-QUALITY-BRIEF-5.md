**เราไม่เดาว่าใครถูก — เราโหลดไฟล์มาอ่าน** สุ่มมา 18 URL ดึงไฟล์ละครั้ง เว้นจังหวะ

- **17 ไฟล์** เป็นเอกสารฝั่งที่ **เลขใน URL คือเลขในรหัสของตัวเอง**
  (`2026-08-26-00124930` → `documents/124930.pdf`) และ**ไม่มีสักไฟล์เดียว**ที่เป็นของอีกฝ่าย
- อีก 1 ไฟล์ (`2128627.pdf`) ตรงกับทั้งสองฝ่าย เพราะ metadata ลงเอกสารเดียวกันซ้ำสองระเบียน
  (`2017-029358`, `2017-029563` เล่ม 134 ง ตอน 99 หน้า 31 เหมือนกันทุกช่อง)

ตัวอย่างที่ชัด — `documents/124930.pdf` เปิดออกมาได้ว่า
"เลม ๑๔๓ ตอนที่ ๑๒๕ ง หนา ๔ … ประกาศเจาพนักงานพิทักษทรัพย" ตรงกับ `2026-08-26-00124930`
(เล่ม 143 ง ตอน 125 หน้า 4) ส่วน `2003-001862` ที่อ้างไฟล์เดียวกันคือ เล่ม 120 ง ตอน 51 หน้า 42
— คนละฉบับโดยสิ้นเชิง

**แต่ไม่ใช่ว่า "ของใหม่ถูกเสมอ"** `documents/29400.pdf` เปิดมาเป็น "เลม ๑๔๑ ตอนที่ ๔๙ ง หนา ๒๑๓"
คือ `2024-013253` ซึ่ง**ไม่ได้**เอาเลขมาจากรหัสตัวเอง ขณะที่ระเบียนปี 2025 ห้าฉบับ
(`2025-01-27-00029400`, `-01-30-`, `-02-04-`, `-02-06-`, `-02-19-` — หน้า 294 เท่ากันหมด ตอนต่างกัน)
ฝังเลข 29400 ไว้ในรหัสตัวเองทุกฉบับ และผิดทั้งห้า

### สิ่งที่เราทำฝั่งเว็บไปแล้ว

เก็บลิงก์ไว้ให้ระเบียนที่ **derive เลขจากรหัสตัวเองได้เพียงฉบับเดียว** ถ้าหลายฉบับ derive ได้
หรือไม่มีใคร derive ได้เลย → **ไม่แสดงลิงก์ให้ใครทั้งนั้น** ผลคือ

```

```

เสียลิงก์ไป 1.5% ดีกว่าพาคนอ่านไปเปิดกฎหมายผิดฉบับ ตัวเลขนี้อยู่ใน
`agg/meta.json.links` ของทุก build เพื่อให้ดูได้ว่าลดลงไหมเมื่อต้นทางแก้

## 3. `id` ที่เป็น null สัมพันธ์กับรูปแบบ URL แบบเป๊ะ 100% (เรื่องนี้ไม่ใช่บั๊ก — เป็นข้อมูลให้ทราบ)

นับ 193,696 ระเบียนในปี 2018 และ 2020–2024 ไม่มีข้อยกเว้นสักระเบียน:

| | URL แบบ `documents/<เลข>.pdf` | URL แบบเล่ม/ตอน/หน้า |
|---|---|---|
| มี `id` | **159,529** | 0 |
| `id` เป็น null | 0 | **34,167** |

รูปแบบที่สองถอดได้ว่า `138D207S0000000000100` = เล่ม 138 · `D`=ง · ตอน 207 · `S`=พิเศษ
(`N`=ปกติ) · ท้ายคือหน้า ตรงกับ `bookNo`/`category`/`section`/`pageNo` ทุกตัวที่เราสุ่มดู
ตัวอักษรที่พบคือ `A`=ก `B`=ข `C`=ค `D`=ง

สัดส่วนทั้งคลัง: `documents/<เลข>.pdf` 770,744 · เล่ม/ตอน/หน้า 34,168 (กระจุกที่ปี 2023 = 29,877)

เข้าใจว่าเป็นสองระบบเผยแพร่ของราชกิจจาเอง ไม่ใช่ความผิดพลาด — แค่อยากยืนยันว่าเราอ่านถูก
และถ้ามันหมายความว่า `id` ใช้เป็นกุญแจไม่ได้ในบางยุค เราเลี่ยงแล้วโดย join ด้วย `pdf_file`

## 4. ปี 2000–2001 ที่เพิ่มเข้ามา — ตรวจแล้วเข้าที่

| | 2000 | 2001 |
|---|---|---|
| meta / taxonomy | 10,537 / 10,537 | 10,096 / 10,097 |
| `source_url` | 100% | 100% |
| `has_text: true` | 115 (1.1%) | 280 (2.8%) |
| `govlevel` เป็น null | 929 (8.8%) | 629 (6.2%) |

ตรงกับที่พวกคุณแจ้งว่า "เกือบทั้งหมดเป็นสแกน ป้ายมาจากชื่อเรื่องอย่างเดียว"
เว็บไม่แสดงปุ่มอ่านเนื้อหาเต็มให้ฉบับที่ `has_text: false` อยู่แล้ว จึงไม่มีผลเสียกับคนอ่าน

**หนึ่งข้อที่ต้องแจ้ง**: `ocr/openlawdata-ocr/<ปี>/index.ndjson` มีถึงแค่ปี **2002–2026**
ปี 2000–2001 ยังไม่มี index ดังนั้นแม้ฉบับที่ `has_text: true` 395 ฉบับนั้นก็ยังอ่านเต็มไม่ได้
ถ้าจะเติม index ให้สองปีนี้ เว็บจะใช้ได้ทันทีโดยไม่ต้องแก้โค้ด

`meta` กับ `taxonomy` ของทั้งสองปีมีจำนวนบรรทัดเท่ากันเป๊ะ และ `pdf_file` ไม่ซ้ำเลย

## 4.1 `id` ซ้ำ 839 ค่า (1,732 ระเบียน) — เอกสารคนละฉบับถือรหัสเดียวกัน

นับทั้งคลัง: `pdf_file` **ไม่ซ้ำเลยสักค่า** (ดีมาก — เราใช้เป็นกุญแจ join อยู่)
แต่ `id` ซ้ำ 839 ค่า และอย่างน้อยบางกรณีเป็นเอกสารคนละฉบับจริง ๆ:

```
meta/2002/2002-10.jsonl   id = 2002-10-09-00102608  (สองบรรทัด)
  pdf_file 2002-002855.pdf · เล่ม 119 ก ตอน 103 หน้า 160
    กฎกระทรวงแบ่งส่วนราชการกรมพัฒนาธุรกิจการค้า กระทรวงพาณิชย์ พ.ศ. ๒๕๔๕
  pdf_file 2002-002856.pdf · เล่ม 119 ก ตอน 103 หน้า 160
    กฎกระทรวงแบ่งส่วนราชการราชบัณฑิตยสถาน พ.ศ. ๒๕๔๕
  ทั้งคู่ source_url = documents/102608.pdf
```

กฎกระทรวงสองฉบับคนละหน่วยงานเป็นเอกสารหมายเลข 102608 พร้อมกันไม่ได้

อีกกรณีคือ `meta/2001/2001-02.jsonl` id `2001-02-22-544654185849684808` ซ้ำสองบรรทัด
(`2001-007564`, `2001-007565` — เล่ม 118 ข ตอน 4 หน้า 127 เหมือนกัน เรื่องเครื่องราชอิสริยาภรณ์)
กรณีนี้อาจเป็นการลงประกาศเดียวกันสองระเบียน ไม่ใช่คนละฉบับแบบข้างบน

## 5. ธง `*_corroborated` ของบางป้ายเป็นศูนย์หรือเกือบศูนย์ทั้งชนิด

นับทั้งคลัง 810,756 ระเบียน:

| แกน | ป้าย | ติดป้าย | corroborated | อัตรา |
|---|---|---|---|---|
| action | **`court_order`** | **438,318** | **1,176** | **0.27%** |
| action | `royal` | 2,552 | 747 | 29% |
| govlevel | **`parliament`** | **13,005** | **4,499** | **35%** |
| topic | `labour` | 4,778 | 2,199 | 46% |
| topic | `university` | 5,845 | 3,412 | 58% |
| — | ป้ายอื่นเกือบทั้งหมด | — | — | 90–100% |

`court_order` เป็นหมวด action ที่ใหญ่ที่สุดในคลัง (54% ของทุกฉบับ) แต่ธง corroborated
แทบไม่เคยติดเลย เราเทียบ revision `d37cb9b9` กับ `4e6bf2ce` ในเดือน 2024-06, 2025-03, 2026-01
แล้ว — **เหมือนกันเป๊ะทั้งสอง revision (7,691 ติดป้าย · 0 corroborated)** จึงไม่ใช่ของใหม่
แต่เป็นแบบนี้มานานแล้ว

คำถามคือ: ตั้งใจให้ `court_order` เป็นป้ายที่มีสัญญาณยืนยันไม่ได้โดยธรรมชาติ
(เพราะยืนยันจากชื่อเรื่องอย่างเดียว ไม่มีสัญญาณที่สอง) หรือเป็นกฎที่ตกหล่น?
คำตอบเปลี่ยนวิธีที่เราแสดงตัวเลขบนเว็บ — รายละเอียดอยู่ท้ายเอกสาร

## ภาคผนวก: เรื่องที่เป็นของฝั่งเรา ไม่ใช่ของพวกคุณ

เว็บเรานับ "จำนวนต่อป้าย" ในหน้าแรก / สถิติ / หน้าหมวด **เฉพาะที่ corroborated**
แต่หน้าสำรวจ (cross-filter) นับ**ทุกป้าย** ผลคือหน้าหนึ่งบอก `court_order` 1,176
อีกหน้าบอก 438,318 — ต่างกัน 373 เท่า และ `parliament` บอก 4,499 กับ 13,005

เป็นข้อบกพร่องของเราเอง มีมาก่อนรอบนี้ และคำตอบข้อ 5 จะเป็นตัวชี้ว่าควรแก้ทางไหน
