ไม่ใช่ "ชั้น OCR ถูกสร้างก่อน taxonomy" แต่แยกเป็นสามกลุ่ม:

    กันไว้โดยเจตนา        10,912   PDF อยู่ครบ สกัดข้อความได้ แต่พิสูจน์ไม่ได้ว่าไฟล์นั้นเป็นของรหัสนี้
    ภาพสแกนจริง            7,263   ไม่มีชั้นข้อความใน PDF ส่วนใหญ่ปี 2002–2004 กำลัง OCR อยู่

กลุ่มแรกมีรายชื่ออยู่ใน `refile_plans/exclude_<ปี>.txt` ตรงกันทีละฉบับ · ทีมนั้นลอง build
โดยไม่กันออกเพื่อพิสูจน์ แล้วด่านตรวจจับได้ทันที: **ปี 2003 มี 290 ฉบับที่หัวกระดาษเป็นของรหัสอื่น

`2021-005366` → `true`, 2,237 true ตรงกับจำนวน entry ใน index ของเดือนนั้น)
**เว็บเปลี่ยนไปใช้ฟิลด์นี้แล้ว** และเลิกอนุมานจาก byte offset

บทเรียนสำหรับรอบต่อไป: เราพิสูจน์ "อะไรเป็นจริง" ได้ถูก แต่เดา "ทำไม" แล้วเสนอวิธีแก้จากการเดานั้น

**ของอื่นที่ทีมนั้นแจ้งกลับ:** `id` backfill แล้ว 1,263,087 ฉบับ · taxonomy ครอบคลุมทุกฉบับใน meta

## 1. ชั้น OCR ตามการขยาย taxonomy ไม่ทัน 21,152 ฉบับ

เรื่องเดียวที่เหลือ และเป็นผลพวงของการแก้รอบที่แล้วเอง

taxonomy ตอนนี้ครอบคลุมเกือบทุก id ใน meta แล้ว (เยี่ยมมาก) แต่**ชั้น OCR ถูกสร้างไว้ก่อนหน้านั้น**
เอกสารที่เพิ่งถูกจัดหมวดจึงไม่มีข้อความ

    เอกสารในเว็บ    790,052
    มีใน index       768,900   (97.32%)
    ไม่มี             21,152   (2.68%)

ปีที่ขาด:

    2021: 5,146    2013:   770    2012:  166
    2003: 4,289    2019:   597    2016:   33
    2004: 3,455    2018:   519    2005:   27
    2002: 1,518    2020:   407    2007:   12
    2017: 1,290    2009:   389    2011:   19
    2014:   908    2015:   349
    2022:   919    2008:   339

**ตรวจมาแล้วว่าไม่ใช่แค่ index ขาด แต่ไฟล์ OCR ไม่มีเอกสารพวกนี้จริงๆ** — ยืนยันสองทาง:

**ทางที่หนึ่ง — index ครอบทุกไบต์ของไฟล์ที่มันอธิบาย**

ตรวจ 48 ไฟล์เดือน ใน 4 ปี (2003, 2013, 2021, 2025) ผ่าน **48/48**:
รายการแรกเริ่มที่ไบต์ 0 · `offset + length` ของทุก record เท่ากับ `offset` ของรายการถัดไปพอดี
(ส่วนต่าง 0 ทุกช่วง) · รายการสุดท้ายจบตรงกับขนาดไฟล์เป๊ะ

ตัวอย่าง `2021-01.jsonl` — 2,237 entries, ช่องว่าง 0, จบที่ 33,529,632 = ขนาดไฟล์

แปลว่า **ไม่มี record ไหนในไฟล์ที่ไม่ถูก index** ฉะนั้น "ไม่มีใน index" = "ไม่มีในไฟล์"

**ทางที่สอง — อ่านไบต์จริงตรงที่เอกสารควรอยู่**

    2021-007568 (มีใน taxonomy, ไม่มีใน index)
      index มีก่อนหน้า : 2021-007567  offset 32,887,991  length 3,447
      index มีถัดไป    : 2021-007611  offset 32,891,438
      32,887,991 + 3,447 = 32,891,438  → ต่อกันสนิท ไม่มีที่ว่าง

    อ่าน bytes 32,887,991–32,891,837 จาก ocr/openlawdata-ocr/2021/2021-01.jsonl
      เจอ doc_id: ['2021-007567', '2021-007611']

ไฟล์**กระโดดข้าม 007568 ถึง 007610 ไปเลย** — 43 ฉบับรวด

**ขอ:** regenerate ชั้น OCR ให้ครอบคลุมชุดที่ taxonomy ครอบคลุมแล้ว **จากนั้นค่อย regenerate
`index.ndjson`** ตามลำดับนี้ เพราะ index สร้างจากไฟล์

**ตรวจซ้ำได้ด้วย:** จำนวน entry ใน `index.ndjson` ทุกปีรวมกัน ควรเท่ากับจำนวน record
ในชั้น OCR และควรครอบคลุมทุก `doc_id` ที่ taxonomy มี ใส่เป็น assertion ได้เลย

**ฝั่งเราจัดการแล้ว ไม่ต้องรีบ:** เว็บอ่าน `index.ndjson` ตอน build แล้วฝัง offset ลงในข้อมูล
เอกสารที่มี offset จึงโหลดข้อความได้ใน **1 request** (จากเดิม 17 requests ~7 วินาที)
ส่วนที่ไม่มี เราไม่แสดงปุ่ม "อ่านเนื้อหาเต็ม" เลย แทนที่จะให้คนกดแล้วรอเพื่อไปเจอว่าไม่มี

## 2. เรื่องเล็กที่เหลือ

**2.1 `source_url` เหลือปีเดียว** — 2002 มี 1,319 จาก 7,163 (18.4%) ขาด 5,844 ฉบับ
ปีอื่นครบหมดแล้ว รวมถึง 2023 และ 2024 ที่รอบที่แล้วยังเป็น 0% กับ 8.4%

**2.2 `id` ยังเป็น null 707,641 จาก 790,122 (89.6%)** — มีค่าจริงเฉพาะ 2025, 2026 และ 2024 บางส่วน
`id` แบบใหม่ประกอบ URL ต้นฉบับได้เอง (ตรวจแล้วว่า `documents/121899.pdf` กับไฟล์ใน `pdf/`
เหมือนกันทุก byte) ถ้า backfill ย้อนหลังได้จะแก้ข้อ 2.1 ไปพร้อมกัน

**2.3 meta 70 ฉบับที่ยังไม่มีใน taxonomy** — จาก 21,152 เหลือ 70 เกือบครบแล้ว

**2.4 field โครงสร้างที่ว่าง** — `pageNo` 2,141 · `section` 1,470 · `bookNo` 1,469
(`bookNo`/`section` ว่างทำให้ค้นด้วย "เล่ม/ตอน/หน้า" ไม่เจอ ซึ่งเป็นวิธีที่นักกฎหมายใช้)

**2.5 เล่มขัดกับวันที่เหลือรายการเดียว และไม่ใช่ข้อผิดพลาด**

    meta/2026/2026-03.jsonl บรรทัด 3302 · 2026-03-28-59674952
      เล่ม 117 (= ค.ศ. 2000) · publishDate 2026-03-28
      "คำวินิจฉัยของศาลรัฐธรรมนูญ คำวินิจฉัยที่ ๒/๒๕๔๓"  (๒๕๔๓ = 2000)
      publishDate_source: "source-contradicts-volume"  ← flag ถูกต้องแล้ว

เป็นเอกสารปี 2000 ที่เพิ่งนำขึ้นเว็บปี 2026 · `publishDate` ที่นี่คือวันอัปโหลด ไม่ใช่วันประกาศ
ทำให้มันไปโผล่ใน "ล่าสุด" ราวกับเป็นเอกสารใหม่ · ถ้าแยก `added_date` ออกมาได้จะตรงความหมายกว่า

**2.6 dataset viewer ยังไม่กลับมา** แต่**น่าจะแค่ยังประมวลผลไม่เสร็จ ไม่ใช่พัง**

    is-valid → ทุกค่าเป็น false
    /rows    → "The server is busier than usual and the response is not ready yet"

ข้อความแบบนี้คือคิวยังไม่ถึง ไม่ใช่ conversion ล้มเหลว · และสาเหตุจริงที่รายงานไปรอบที่แล้ว
**แก้แล้ว: `extracted` เหลือรูปร่างเดียวจาก 8 แบบ** ฝากเช็คซ้ำอีกครั้งหลังคิวเดิน
