### 1. ลิงก์ PDF ต้นฉบับ — มาแล้วบางส่วน ขอบคุณมาก 🎉

**อัปเดต 2026-09-14:** `source_url` ถูกเพิ่มเข้ามาใน `meta` แล้ว ฝั่งเว็บ implement รองรับเรียบร้อย
รายงานสถานะที่วัดได้ตอนนี้:

    1885-01 .. 2012-12   มี source_url แล้ว        923,572   (66.5%)
    2013-01 .. 2024-11   ยังไม่มีเลย               382,608   (27.6%)  ← ช่องว่างที่เหลือ
    2024-12 เป็นต้นไป    derive จาก id ได้เอง       82,411   (5.9%)
                                              รวม 1,388,591

**format มีแบบเดียว** ทั้งหมด — `https://ratchakitcha.soc.go.th/documents/N.pdf`
host เดียว https ล้วน จากตัวอย่าง 27,555 รายการที่สุ่มข้าม 128 ปี ไม่มีรูปแบบอื่นเลย
สะอาดมาก ทำให้ฝั่งเราเก็บแค่ตัวเลขแทน URL เต็มได้

**ปี 2024-12 เป็นต้นไปไม่ต้องทำอะไร** — `id` (เช่น `2026-09-01-00121899`) มีเลขเอกสารอยู่ในตัวแล้ว
ประกอบ URL เองได้ ตรวจแล้วว่า `documents/121899.pdf` จากเว็บราชกิจจาฯ กับ
`pdf/2026/2026-09/2026-09-01-00121899.pdf` บน HF **เหมือนกันทุก byte**
(sha256 `d4ffbeab…c57e319`) จึงไม่จำเป็นต้อง backfill ช่วงนี้

**ที่เหลือขอจริงๆ คือช่วง 2013-01 ถึง 2024-11** — 382,608 รายการ (27.6% ของคลัง)
ตอนนี้ไม่มีทั้ง `source_url` และ `id` มีแต่ `pdf_file` แบบ `2014-009286.pdf`
ซึ่ง join กับอะไรไม่ได้เลย ทางเดียวคือ `zip/2014/2014-06.zip` ทั้งก้อน

**สองเรื่องเล็กที่เจอระหว่าง implement — ฝากดูด้วย:**

*(ก) เลขเอกสารมีตั้งแต่ 5 ถึง 18 หลัก* — ส่วนใหญ่ 7 หลัก แต่มีกลุ่มที่ยาว 18 หลัก เช่น

    meta/2001/2001-01.jsonl บรรทัด 87-89   2001-008331..8333
      https://ratchakitcha.soc.go.th/documents/544639616062325576.pdf
    meta/2000/2000-07.jsonl บรรทัด 30-33   2000-003802..3805
      https://ratchakitcha.soc.go.th/documents/538558279207355208.pdf
    meta/1996/1996-01.jsonl บรรทัด 7        1996-006865
      https://ratchakitcha.soc.go.th/documents/496665807766422344.pdf

ตรวจแล้ว **เปิดได้จริงทั้งหมด** ไม่ใช่ข้อมูลเสีย แต่เป็นกับดักสำหรับคนเอาไปใช้ต่อ:
เกิน `Number.MAX_SAFE_INTEGER` (9,007,199,254,740,991) ถ้าใครเก็บเป็นตัวเลขใน JSON
แล้วอ่านด้วย JavaScript จะได้ `544639616062325600` — **ลิงก์ไปเอกสารผิดฉบับ ซึ่งแย่กว่าไม่มีลิงก์**
(int64 ใน Parquet ไม่มีปัญหา เพราะยังไม่ถึง 2^63)
ฝั่งเราแก้แล้วโดยเก็บเป็น string เมื่อเกินขอบเขต — ฝากเขียนเตือนไว้ใน README ด้วยจะดีมาก

*(ข) มี null ปนอยู่ ~1.4% ในปีที่มี field แล้ว* — จากตัวอย่าง 27,940 รายการ พบ null 385 รายการ
กระจุกที่ 2002 ×145 · 1997 ×106 · 1998 ×99 · 1963 ×34
(เช่น `meta/2002/2002-01.jsonl` หัวไฟล์ 13 รายการแรกเป็น null ทั้งหมด)

### 2. dataset viewer บน HF พังทั้ง 3 config

    GET /is-valid?dataset=open-law-data-thailand/soc-ratchakitcha
    {"preview": true, "viewer": false, "search": false,
     "filter": false, "statistics": false}

คนที่เปิดหน้า dataset เห็นได้แค่ไม่กี่แถวแรก จะ search / filter / ดู statistics ไม่ได้เลย
สาเหตุคนละเรื่องกันทั้งสาม:

**config `meta` — schema ไม่ตรงกันระหว่าง shard**

    Couldn't cast ... because column names don't match

- ไฟล์รุ่นเก่า 1,306,180 records ไม่มีคอลัมน์ `id`
- ไฟล์รุ่นใหม่ 82,411 records **มี** `id`
- รอยต่อ: `meta/2024/2024-11.jsonl` (เก่า) → `meta/2024/2024-12.jsonl` (ใหม่)
- ซ้ำ: `no` ถูก infer เป็น `int64` ใน shard หนึ่ง แต่ schema ประกาศเป็น `string`

**config `iapp` — nested struct ไม่ตรงกัน** ที่ `data.ocr_results`
บาง shard มี child เพิ่ม (`json_result`) บาง shard ไม่มี

**config `openlawdata` — วันที่ที่ไม่มีอยู่จริงในปฏิทิน**

    Failed to parse string: '1946-02-29' as a scalar of type timestamp[s]

ปี 1946 (พ.ศ. 2489) **ไม่ใช่ปีอธิกสุรทิน** — 29 กุมภาพันธ์ปีนั้นไม่มีอยู่จริง
สแกน `meta/` และ `taxonomy/` ทั้งหมดแล้ว **ไม่มี** วันที่ผิดปฏิทินเลยสักรายการ
แปลว่าค่านี้อยู่ในชั้น OCR — น่าจะเป็น `announcement_date` ซึ่งแกะจากตัวอักษรในเอกสาร
(`๒๙ กุมภาพันธ์ ๒๔๘๙`) แล้วแปลงเป็น ค.ศ. โดยไม่ตรวจว่าวันนั้นมีจริงไหม

หาให้เจอด้วย:

    grep -ln '1946-02-29' ocr/openlawdata-ocr/*/*.jsonl

**ขอ:**

- เติม `id` ให้ครบทุก record (ค่าว่างเป็น null ได้) และ cast `no` เป็น string ทุก shard
- ประกาศ `features` แบบชัดเจนใน README แทนการให้ Arrow เดา
- validate วันที่ด้วย `datetime.date.fromisoformat` ก่อนเขียน — วันที่แกะไม่ได้ให้เป็น
  **null** ไม่ใช่ค่าเดา
- ยังไม่มี config สำหรับ `taxonomy/` เลย — โหลดผ่าน `datasets` ไม่ได้ ขอเพิ่มด้วย

### 3. taxonomy 673 รายการถูกเปลี่ยนปีจาก 1998 เป็น 2025

`taxonomy/2025/2025-07.jsonl` มี 4,786 records แต่ **673 รายการเป็นเอกสารปี 1998**
ที่ถูกยัดเข้ามาในพาร์ทิชัน 2025-07 พร้อมวันที่และเล่มที่ถูกเขียนทับใหม่

พิกัด — `taxonomy/2025/2025-07.jsonl` **บรรทัดที่ 1**:

    taxonomy ว่า : doc_id=1998-001218  year=2025  month=2025-07
                   volume=142  part="244 ง"  publish_date=2025-07-14
    meta ว่า     : meta/1998/1998-08.jsonl บรรทัด 1218
                   bookNo=115  section=64  publishDate=1998-08-11

`meta` ถูก — เล่ม 115 = ค.ศ. 1998 และชื่อเรื่องเป็นคำสั่งพิทักษ์ทรัพย์เด็ดขาด
ศาลแพ่งธนบุรี ซึ่งสอดคล้องกับปี 1998

องค์ประกอบของ 673 รายการ:

- ปีจริงจาก doc_id : **1998 ทั้ง 673 รายการ**
- volume ที่ถูกใส่ : **142 ทั้ง 673 รายการ** (= 2025)
- agency          : เจ้าพนักงานพิทักษ์ทรัพย์ ×660 · กรมทรัพยากรธรณี ×6 · null ×5
- publish_date ที่ถูกใส่ : 2025-07-30 ×306 · 2025-07-23 ×301 · 2025-07-29 ×64

**เป็นไฟล์เดียวในทั้ง tree ที่มีปัญหานี้** — 673 จาก 776,472 records

**ขอ:** เพิ่ม assertion ใน pipeline — `doc_id[:4] == str(year)` ต้องจริงเสมอ
ตอนนี้ผิดแค่ไฟล์เดียว แต่เป็น class ของบั๊กที่เงียบมากและตรวจง่ายมาก

### 4. meta 137 รายการมี publishDate ที่ขัดกับเล่ม

มี invariant ที่ใช้ตรวจได้: **ค.ศ. = เล่ม + 1883**
ตรวจกับข้อมูลจริง — จริง 1,386,099 จาก 1,386,848 รายการ (99.946%)

ข้อยกเว้นที่ต้องยอม ไม่ใช่บั๊ก:

- คลาดเคลื่อน ±1 ปี — ตอนหนึ่งของเล่มเดียวกันพิมพ์คร่อมปีใหม่ได้ตามปกติ
- ก่อนปี 1950 — เล่มยุคต้นไม่ได้ผูกกับปีปฏิทินแบบ 1:1
  (เช่น `meta/1885/1885-01.jsonl` บรรทัด 1 เล่ม=1 ปี 1885)

ตัดสองข้อนั้นออกแล้วเหลือ **137 รายการที่ผิดจริง** และทั้ง 137 มี `doctitle` ครบ
— ไม่ใช่ record ที่แกะไม่สำเร็จ แต่เป็น record ที่สมบูรณ์และวันที่ผิด

กระจุกอยู่ที่:

    meta/2013/2013-11.jsonl    70
    meta/2023/2023-02.jsonl    30
    meta/1983/1983-05.jsonl    15
    meta/2023/2023-03.jsonl    11
    meta/1970/1970-01.jsonl     6
    meta/2023/2023-01.jsonl     2
    meta/1953/1953-10.jsonl     1
    meta/2016/2016-06.jsonl     1
    meta/2026/2026-03.jsonl     1

เปิดดู 4 รายการ — **ทั้ง 4 เล่มถูก วันที่ผิด** และเนื้อชื่อเรื่องยืนยันฝั่งเล่ม:

`meta/2013/2013-11.jsonl` บรรทัด 2146 — `2013-028472`
เล่ม 122 → 2005 · publishDate=2013-11-11 · คลาด 8 ปี
ชื่อเรื่องอ้างคดีหมายเลขแดงที่ ๓๐๕๖/**๒๕๔๗** (= 2004) สอดคล้องกับ 2005

`meta/1983/1983-05.jsonl` บรรทัด 345 — `1983-002946`
เล่ม 90 → 1973 · publishDate=1983-05-11 · คลาด 10 ปี
ชื่อเรื่อง "แก้คำผิด … เล่ม ๘๙ ตอนที่ ๑๙๓" — เล่ม 89 = 1972 สอดคล้องกับ 1973

`meta/1970/1970-01.jsonl` บรรทัด 691 — `1970-009777`
เล่ม 139 → 2022 · publishDate=**1970-01-01** · คลาด 52 ปี
ชื่อเรื่องคือการจดทะเบียนอาคารชุด "เดอะทรี พัฒนาการ-เอกมัย" ซึ่งเป็นคอนโดยุคปัจจุบัน
**1970-01-01 คือ Unix epoch** — เป็นค่า sentinel ของ "แปลงวันที่ไม่สำเร็จ" ชัดเจน
มี 6 รายการในไฟล์นี้

`meta/2023/2023-02.jsonl` บรรทัด 735 — `2023-005022`
เล่ม 138 → 2021 · publishDate=2023-02-23 · คลาด 2 ปี

**ผลพวงที่ต้องรู้ก่อนแก้:** id และพาร์ทิชันของ zip ถูกตั้งตามวันที่ที่ผิดไปด้วยแล้ว
ตรวจแล้วว่า `2013-028472.pdf` อยู่ใน `zip/2013/2013-11.zip` จริง
ฉะนั้น **แก้ publishDate ได้โดยไม่ทำ link พัง แต่ห้ามเปลี่ยน id** — id ที่มีอยู่ถูกใช้อ้างอิงไปแล้ว
แนะนำ: แก้ `publishDate` ให้ถูก คง `pdf_file`/`doc_id` ไว้ และเพิ่ม field บอกว่าถูกแก้

**ขอ:**

- ใส่ invariant `ค.ศ. = เล่ม + 1883 (±1, เฉพาะปี ≥ 1950)` เป็น test ใน pipeline
- เลิกใช้ `1970-01-01` เป็นค่าแทนวันที่ว่าง — ให้เป็น **null**

### 8. index บอก byte offset ของชั้นข้อความ

ตอนนี้เว็บดึงข้อความเต็มจาก `ocr/openlawdata-ocr/` ด้วย HTTP Range แล้วไล่หา
แบบ k-way narrowing เพราะไม่รู้ว่า record อยู่ที่ byte ไหน —
**17 requests ต่อเอกสาร 1 ใบ ใช้เวลา ~7 วินาที**

ถ้ามีไฟล์ index สักไฟล์:

    ocr/openlawdata-ocr/index.jsonl
    {"doc_id": "2002-007122", "file": "2002/2002-01.jsonl",
     "offset": 145238, "length": 8814}

จะเหลือ **1 request** และโหลดทันที นี่คือรายการที่คุ้มที่สุดในเอกสารนี้
ต่อความพยายามที่ลงไป

ระหว่างนี้: `ocr/openlawdata/` (297 ไฟล์) ยังซ้ำกับ `ocr/openlawdata-ocr/`
(297 ไฟล์) อยู่ ตาม README จะลบหลัง 2026-12-31 — ทำได้เร็วกว่านั้นก็ดี
จะลดขนาด repo ลงครึ่งหนึ่งในชั้นที่หนักที่สุด

### 9. field ที่ควรแกะเพิ่มสำหรับประกาศล้มละลาย

ประกาศเจ้าพนักงานพิทักษ์ทรัพย์เป็นเอกสารกลุ่มใหญ่ที่สุดกลุ่มหนึ่ง
(660 จาก 673 รายการในข้อ 3 เป็นกลุ่มนี้) และเป็นกลุ่มที่คนค้นด้วย **ชื่อคน**
มากที่สุด — ตรวจว่าคู่ค้าติดล้มละลายไหม ตรวจชื่อตัวเอง

ข้อมูลอยู่ในชื่อเรื่องอยู่แล้วในรูปแบบที่คงที่มาก:

    "ประกาศเจ้าพนักงานพิทักษ์ทรัพย์ เรื่อง คำสั่งพิทักษ์ทรัพย์เด็ดขาด
     [ศาลล้มละลายกลาง คดีหมายเลขแดงที่ ๓๐๕๖/๒๕๔๗ นายคงศักดิ์ แสนสมบัติ ลูกหนี้]"

**ขอ:** แกะเป็น field — `court`, `case_number`, `debtor_name`, `debtor_type`
(บุคคล/นิติบุคคล) จะเปิดทางให้ทำ search ตามชื่อได้อย่างถูกต้อง
แทนที่จะให้แต่ละคนไป regex ชื่อเรื่องเอง
