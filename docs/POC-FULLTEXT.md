# PoC: ค้นเนื้อหาเต็มโดยไม่มีเซิร์ฟเวอร์

ทดลองกับ **ปี 2025 · 49,127 ฉบับ · ข้อความจริง 684 MB** ดึงจากชั้น `ocr/` ของต้นทาง
สคริปต์อยู่นอก repo (scratchpad) — ยังไม่ใช่โค้ดที่ใช้งานจริง

คำถามที่ต้องตอบ 3 ข้อ · **ตอบครบแล้วทั้ง 3 และผ่านทั้งหมด**

---

## 1. index จริงใหญ่เท่าไหร่ — ตอบแล้ว

| ชั้น | ขนาด | หน้าที่ |
|---|---|---|
| `dict.bin` | **4.02 MB** | trigram → ตำแหน่งใน bitmap และ postings |
| `bitmap.bin` | **0.38 MB** | บล็อกไหนมี trigram นี้ (บล็อกละ 4,096 ฉบับ) |
| `postings.bin` | **58.62 MB** | เลขเอกสารจริง delta + varint |
| `ids.json` | 1.13 MB | เลขลำดับ → doc_id (ควรเป็น binary ไม่ใช่ JSON) |
| **รวม** | **64.16 MB** | = **9.4% ของขนาดข้อความ** |

ประมาณการทั้งคลัง 810,756 ฉบับ (×16.5): **postings ~0.97 GB** · dict อิ่มตัวไม่โตตามฉบับ ·
รวมแล้วราว **1 GB = 50 ไฟล์ @20 MB** เทียบกับเพดาน Cloudflare Pages 20,000 ไฟล์ (free)

### สิ่งที่ไม่ได้คาดไว้: ครึ่งหนึ่งของคำศัพท์เป็นขยะ OCR

เดือนเดียว 4,385 ฉบับให้ 174,715 trigram — **49% โผล่แค่ฉบับเดียว** และเปิดดูแล้วเป็นขยะล้วน
(`่ปข`, `ษม"`, `“CH`, `TYD`) มีแค่ 40% ที่เป็นอักษรไทยล้วน

| ตัดที่โผล่ ≤ n ฉบับ | เหลือคำศัพท์ | เสีย postings |
|---|---|---|
| 1 | 51.3% | 1.5% |
| **2** | **38.7%** | **2.3%** |
| 5 | 26.2% | 3.8% |

ตัดที่ ≤2 ทำให้ `dict.bin` เล็กลง **60%** (3.66 → 1.47 MB ในเดือนนั้น) โดย postings แทบไม่ขยับ

**ข้อควรระวัง** — trigram ที่ถูกตัดต้องแปลว่า "ไม่ใช้เป็นเงื่อนไข" ไม่ใช่ "ไม่มีผลลัพธ์"
ไม่งั้นทุกตัวที่ตัดจะกลายเป็นรูโหว่ในคลังแทนที่จะเป็นแค่ความแม่นยำที่ลดลง

## 2. สร้างนานแค่ไหน และค้นถูกไหม — ตอบแล้ว

**สร้าง: 30 วินาที ต่อหนึ่งปี · หน่วยความจำสูงสุด 800 MB** (Python ล้วน ไม่ได้ปรับแต่ง)
ทั้งคลัง 27 ปีจึงราว 13 นาที ถ้าทำทีเดียว — แต่ควรทำแยกรายเดือนและทำซ้ำเฉพาะเดือนที่ต้นทางเปลี่ยน

**ความถูกต้อง** เทียบกับการไล่หาในข้อความจริงทั้งเดือน:

| คำค้น | ผลจาก index | จริง | recall | precision |
|---|---|---|---|---|
| เจ้าพนักงานพิทักษ์ทรัพย์ | 2,408 | 2,406 | 100% | 99.9% |
| องค์การบริหารส่วนตำบล | 695 | 690 | 100% | 99.3% |
| พระราชกฤษฎีกา | 17 | 17 | 100% | 100% |
| สำนักงานคณะกรรมการกำกับหลักทรัพย์ | 34 | 32 | 100% | 94.1% |
| ยโสธร | 33 | 33 | 100% | 100% |

**recall 100% ทุกคำ** ส่วนตัวที่เกินมาคือ false positive ของ trigram ซึ่งกรองทิ้งได้ตอนดึง
ข้อความมาทำ snippet อยู่แล้ว

### ต้องอ่านกี่ไบต์ต่อหนึ่งคำค้น

อ่าน trigram ครบทุกตัวแพงเกินจำเป็น — ใช้แค่ **3 ตัวที่หายากที่สุด** แล้วไปยืนยันกับข้อความ:

| คำค้น | ครบทุก trigram | 3 ตัวหายากสุด | ผู้สมัครที่ต้องยืนยัน |
|---|---|---|---|
| เจ้าพนักงานพิทักษ์ทรัพย์ | 748 KB | **83 KB** | 27,763 (คำตอบจริง 27,707) |
| สำนักงานคณะกรรมการกำกับหลักทรัพย์ | 642 KB | **6.9 KB** | 363 (จริง 180) |
| พระราชกฤษฎีกา | 195 KB | **2.1 KB** | 416 (จริง 416) |
| ผังเมืองรวม | 92 KB | **7.9 KB** | 663 (จริง 588) |
| ฟอกเงิน | 19 KB | **7.5 KB** | 246 (จริง 246) |
| ยโสธร | 2 KB | **1.6 KB** | 269 (จริง 269) |

**ส่วนใหญ่อ่าน 2–8 KB ต่อคำค้น** — เท่ากับรูปเล็กหนึ่งรูป

## 3. Cloudflare Pages ทำ Range บนไฟล์ 20 MB ได้ไหม — **ได้ และเร็ว**

วางไฟล์ทดสอบ 20 MiB ที่ `/probe/range-20mb.bin` เนื้อในเป็นตัวนับ 8 ไบต์เรียงกัน
ค่าที่ byte 8n เท่ากับ n เพื่อพิสูจน์ว่าไบต์ที่ได้คือไบต์ที่ขอ (ลบออกแล้วหลังวัดเสร็จ)

```
HTTP/2 200 · content-type: application/octet-stream · accept-ranges: bytes

Range: bytes=8000000-8004095
→ HTTP/2 206 · content-range: bytes 8000000-8004095/20971520 · ได้ 4,096 ไบต์
→ ค่าตัวแรก 1,000,000 · ตัวสุดท้าย 1,000,511 — ตรงช่วงที่ขอเป๊ะ
```

ขอ 4 KB จากแปดตำแหน่งกระจายทั่วไฟล์:

| ตำแหน่ง | ผล | ไบต์ที่ได้ | เวลา |
|---|---|---|---|
| 100 · 3 M · 7 M · 11.5 M · 16 M · 19 M · 0.5 M · 12.3 M | 206 ทุกครั้ง | 4,096 ทุกครั้ง | **49–68 ms** |

**ตำแหน่งในไฟล์ไม่มีผลต่อความเร็วเลย** — ต้นไฟล์กับท้ายไฟล์เท่ากัน แปลว่า edge เสิร์ฟจาก
ของที่ cache ไว้ ไม่ได้ไล่อ่านตั้งแต่ต้น เทียบกับการดึงทั้งไฟล์ 20 MB ที่ใช้ 519 ms

### แปลว่าการค้นหนึ่งครั้งจะใช้เวลาเท่าไหร่

หนึ่งคำค้น = อ่าน bitmap หนึ่งแถว + postings 3 ชุด ≈ **4 Range** ยิงพร้อมกันได้
→ ราว **50–70 ms** บวกเวลาโหลด `dict.bin` ครั้งแรกครั้งเดียว (4 MB ≈ 150 ms แล้ว cache)

## ที่ยังไม่ได้ทำ และต้องคิดต่อ

- **ตัวเลขทั้งหมดมาจากปี 2025 ปีเดียว** ซึ่งเป็นปีที่ OCR คุณภาพดีที่สุด ปีเก่าที่เป็นภาพสแกน
  จะมีขยะมากกว่า คำศัพท์จะบานกว่านี้
- **ยังไม่ได้ทดสอบบนเบราว์เซอร์จริง** — ตัวเลข latency ข้างบนเป็นการอ่านจากดิสก์ในเครื่อง
- **`dict.bin` ทั้งคลังอาจโตเกินกว่าจะโหลดทีเดียว** ถ้าเกิน ~10 MB ต้องแบ่งชั้นเพิ่มอีกชั้น
  (dict ของ dict) หรืออ่านด้วย Range เหมือนชั้นอื่น
- **ยังไม่ได้ตัดสินว่าจะ mirror ตัวข้อความ 10 GB ไหม** — index กับข้อความเป็นคนละเรื่อง
  index คือความสามารถใหม่ ส่วนการ mirror ข้อความแค่ทำให้เร็วขึ้น

## สรุป: เดินได้ และถูกกว่าที่คิด

| คำถาม | คำตอบ |
|---|---|
| index ใหญ่ไหม | ~1 GB ทั้งคลัง = 50 ไฟล์ จากเพดาน 20,000 |
| สร้างนานไหม | 30 วินาทีต่อปี · ทำแยกรายเดือนได้ ไม่ต้องทำใหม่ทั้งคลัง |
| ค้นถูกไหม | recall 100% · precision 94–100% |
| อ่านกี่ไบต์ | 2–8 KB ต่อคำค้นโดยทั่วไป · แย่สุด 83 KB |
| Pages ทำ Range ได้ไหม | ได้ · 206 · 50 ms ไม่ว่าตำแหน่งไหนในไฟล์ |

**ไม่ต้องมี backend ไม่ต้องมี D1 ไม่ต้องมี DuckDB-Wasm** — ของเดิมที่เรามีอยู่ (Static Files +
Range + คิดเลขในเบราว์เซอร์) รับงานนี้ได้

### ก้าวถัดไปถ้าจะทำจริง เรียงตามลำดับ

1. **ทดสอบบนเบราว์เซอร์จริง** — ตัวเลข 50 ms ข้างบนมาจาก curl ยังไม่ได้ผ่าน
   fetch + CORS + การถอด varint ใน JavaScript
2. **ทดสอบกับปีเก่า** เช่น 2005 ที่ OCR แย่กว่า เพื่อดูว่าคำศัพท์บานแค่ไหน
3. **ตัดสินเรื่อง `dict.bin`** ถ้าทั้งคลังเกิน ~10 MB ต้องแบ่งชั้นเพิ่มหรืออ่านด้วย Range
4. แล้วค่อยเขียนของจริงเข้า pipeline
